Scope: website-only email confirmation, cancellation, suppression and durable send protection. Production sending and release are held for owner review. The current provider verification status and exact-source results are in CURRENT_HANDOVER; do not infer completion from this implementation description.

## Implementation

The durable adapter uses Resend for plain-text delivery, an isolated Upstash Redis Free store in Sydney with eviction disabled, and the existing Vercel host's daily job. No app database, account, entitlement, pricing, Next.js dependency or lockfile change. The older external-webhook adapter remains available for compatibility but is not the selected new implementation. The four earlier Resend drafts stay unpublished and no native Resend automation is running; using both paths would risk duplicate delivery.

An explicit opt-in saves the exact consent text/version and time. The only initial email asks for confirmation. A signed seven-day link opens a read-only page; an explicit POST starts the sequence. Scanners/prefetches cannot confirm through GET. Tokens bind the action and hashed recipient, never contain an email address and are protected against modification. No tracking scripts, third-party assets or referrer are loaded by the standalone confirmation/cancellation pages. Both are noindex.

An atomic Lua reservation precedes every send, including confirmation, with an additional state check at dispatch. A stable provider idempotency key adds protection inside Resend's 24-hour window. Our reservation has no automatic expiry: unknown outcomes, interrupted sends or uncertain acknowledgements remain held and never automatically resend. Repeated submissions and confirmations do not reset dates, restart a cancelled/completed sequence or send another confirmation. A missing store-identity marker fails closed instead of silently rebuilding an empty delivery ledger. This is normal operational duplicate protection, not an absolute exactly-once delivery guarantee under arbitrary provider data loss.

Unsubscribe requires no login and remains available with sending disabled. It removes the address and queued work atomically. GET shows a confirmation; POST also supports RFC8058 one-click. Signed Resend bounce, complaint and suppression events are raw-body verified with a five-minute timestamp bound and rotating signatures. Applying the event again is idempotent. A message already dispatched cannot be recalled; cancellation prevents remaining messages. No public test-clock or state-reset endpoint exists.

Addresses are AES-256-GCM encrypted at rest. Keyed recipient hashes support deduplication. Completed/withdrawn/suppressed addresses are removed immediately; the daily retention job removes remaining abandoned encrypted addresses after30days. Minimal consent, no-repeat, reservation and suppression records remain. Short-lived daily keyed IP buckets limit abuse without storing raw IPs. Keep the token/encryption secret and namespace stable; never rotate them or restore/flush an older store while sending is active. Pause, reconcile provider results and obtain the appropriate operational approval before recovering held sends or lost state.

Caps: at most3new requests per daily IP bucket,20new requests/hour,500enrollments in this pack namespace,80reserved emails/UTCday and2400/UTCmonth. Provider failures still consume reservations. No paid upgrade or automatic overage is requested. Free account exhaustion fails closed. The worker processes at most20due records per run with a time budget. It sends only the latest due note after a delayed run, never a catch-up burst. Daily scheduling means a note can arrive on the first run after its day2/5/8 threshold; this is not exact-to-the-minute delivery. Sequence ends after the final note.

## Acceptance evidence and gates

The synthetic integration suite executes the real Lua against the provisioned Redis store with mocked delivery. It covers the complete day0/2/5/8 schedule; concurrent requests, confirmations and workers; restart recovery; cancellation before confirmation and during a wait; cancellation after reservation; signed-event suppression/replays; uncertain delivery beyond24hours; delayed workers; retention; quotas and store-identity failure. It does not prove SMTP delivery, real inbox placement, provider webhook transport or eight days of elapsed wall-clock operation.

Real-inbox acceptance must use only the designated owner test inbox, an isolated acceptance namespace and test mode on a preview deployment. Real Resend domain verification is checked before each actual provider send. Branch-preview variables only; production mode additionally requires the explicit live-approval flag, production environment, webhook secret and scheduler credential. No analytics/experiment is enabled by this work.

Before release, record actual sender verification; authenticated inbox receipt/authentication results; confirmation GET versus POST; a real welcome and the three accelerated test notes; concurrent duplicate retries; unsubscribe/one-click; authenticated bounce/complaint callback transport; and preview desktop/mobile behaviour. Accelerated clock/state fixtures must be labelled, remain private to synthetic acceptance data and cannot be exposed to public callers. Failure or a pending provider result keeps customer sending disabled. Production still needs the owner's explicit approval after the report.

Stop/rollback: disable PACK_CAMPAIGN_ENABLED and pause scheduled delivery, retaining the store and secrets. Leave unsubscribe and provider event endpoints working to preserve withdrawals. Remove only temporary test callback access when testing ends. Do not delete suppression records, clear reservations, restart a native automation or restore an older ledger as a retry mechanism. Investigate any held count or provider errors before another send decision.
